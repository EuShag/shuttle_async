# shuttle_async

**shuttle_async** — экспериментальная библиотека задач на корутинах C++23 и исполнителей, автор **Eugenii Shagunov**. В проект входят корутинные задачи, асинхронные и однопоточные исполнители, структурированные области дочерних задач, кооперативная отмена и динамически размещаемое общее состояние задачи.

Проект активно разрабатывается и пока не является готовой к промышленной эксплуатации библиотекой. Тесты и замеры ниже описывают проверенные сценарии, но не доказывают абсолютную корректность или производительность.

## Возможности

- `AsyncTask<T>` для асинхронной работы и `BlockingTask<T>` для явной синхронной границы.
- `ThreadPoolExecutor` с локальными Chase–Lev-деками, общей входящей очередью, случайным выбором очереди для кражи и объединением уведомлений воркеров.
- `OneThreadExecutor` для последовательного выполнения на выделенном потоке.
- `CoroScope` и `JoinableScope` для управления временем жизни дочерних задач.
- Перемещаемые, но некопируемые `AsyncPromise<T>` и `AsyncFuture<T>` на базе динамически размещаемого `AsyncSharedState<T>`.
- Пользовательский аллокатор для размещения общего состояния и аллокации библиотеки через mimalloc.
- Ошибки операций на основе `std::expected` и кооперативная отмена задач.

Таймеры и асинхронный ввод-вывод пока не реализованы. **Асинхронный ввод-вывод Win32 есть в планах**, но сейчас его API отсутствует.

> ⚠️ **Критическое предупреждение по безопасности:** Метод `launchImmediate` выполняет корутину синхронно на вызывающем потоке до первой точки приостановки. Использовать `co_await` внутри такого режима разрешается **строго в рамках одного и того же потока (например, совместно с ThreadPinnedExecutor / OneThreadExecutor)**. Ни в коем случае не допускайте миграции на другие потоки или пулы потоков внутри Immediate-задач. Смена контекста выполнения на другой поток нарушит иерархию Structured Concurrency и **приведёт к неопределённому поведению (UB)**.



## Требования

- Компилятор C++23 с поддержкой корутин и `std::expected`.
- CMake версии 3.21 или новее.
- Инициализированные Git submodules (mimalloc и concurrentqueue).

Сейчас библиотека разрабатывается и тестируется на Windows с MinGW/CLion. Другие компиляторы и операционные системы требуют дополнительной проверки.

## Сборка и тесты

В PowerShell или другой оболочке, где доступны CMake и компилятор C++23:

```powershell
git submodule update --init --recursive
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DASYNC_BUILD_TESTS=ON -DASYNC_BUILD_EXAMPLES=ON
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

Для Debug используйте отдельную директорию сборки. В генераторе с несколькими конфигурациями укажите `--config Debug` или `--config Release`. При сборке Debug с GCC необходим флаг `-foptimize-sibling-calls`, чтобы избежать роста стека при symmetric transfer корутин; цель CMake добавляет его автоматически. Полный масштабный стресс-тест может занимать несколько минут и сильно нагружать процессор.

Автономная сборка CMake использует зависимости из `external/`. Цель библиотеки — `async::async`; она экспортирует каталог `include/` и требование C++23.

## Примеры

- [`examples/thread_pool_tasks.cpp`](examples/thread_pool_tasks.cpp) запускает `AsyncTask` в пуле потоков и получает результат.
- [`examples/shared_state_custom_allocator.cpp`](examples/shared_state_custom_allocator.cpp) создаёт общее состояние с пользовательским аллокатором и использует перемещаемые promise/future endpoints.

Сборка примеров:

```powershell
cmake --build build --config Release --target async_thread_pool_example async_shared_state_example
```

`JoinableScope` ожидает завершения дочерних задач при явном join и при разрушении. Не захватывайте в корутинах ссылки на объекты, время жизни которых заканчивается раньше join. `BlockingTask::get()` блокирует текущий поток ОС; не вызывайте его из worker-а, если задача для продолжения требует тот же worker.

## Архитектура и владение

```text
AsyncTask<T> / BlockingTask<T>
       | завершение
       v
AsyncPromise<T> <-> AsyncSharedState<T> <-> AsyncFuture<T>
       | планирование                       | продолжение waiter-а
       +------------------- IExecutor <-----+
                               |
                    +----------+----------+
                    v                     v
           ThreadPoolExecutor      OneThreadExecutor
                    |
       локальные Chase–Lev-деки + общая входящая очередь
       случайная кража задач + объединение пробуждений
```

`AsyncSharedState` не создаётся пользователем как объект на стеке. `makeAsyncState` динамически выделяет блок состояния и возвращает move-only endpoints `AsyncPromise` и `AsyncFuture`. Пользовательский аллокатор позволяет контролировать размещение этого блока.

## Тесты и замеры (Производительность)

Масштабный стресс-тест планировщика проводился на процессоре **Intel Core i9-14900KF** (24 ядра, 32 потока) в конфигурации компиляции **Release с максимальной оптимизацией (-O3)**. В коде полностью отсутствуют какие-либо логи или диагностический вывод, что позволило замерить чистую производительность lock-free алгоритмов.

### Профили нагрузки:
1. **Профиль «Много малых задач» (Small tasks):** 50 000 атомарных задач, 3 повтора. Тест на наносекундный оверхед координации и пропускную способность шины кэша.
2. **Профиль «Большие задачи» (Large tasks):** 5 000 тяжелых задач, 3 повтора. Тест на утилизацию чистой вычислительной мощности ядер при минимальном обращении к очередям.
3. **Профиль «Неравномерные задачи» (Uneven tasks):** 10 000 задач, 3 повтора. Смесь из 10% тяжелых и 90% легких задач. Эмуляция хаотичной нагрузки реального игрового кадра.

## Roadmap

- Продолжить стресс-проверки времени жизни задач, остановки исполнителей, гонок пробуждения и путей отказа.
- Улучшить воспроизводимость бенчмарков и сравнивать изменения планировщика на разных нагрузках и toolchain.
- **Спроектировать и реализовать асинхронный ввод-вывод для Win32**, включая отмену, доставку завершения и интеграцию с executor API. Это план; API Win32 I/O пока нет.
